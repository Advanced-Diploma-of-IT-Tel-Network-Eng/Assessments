# REQUIREMENTS REPOSITORY AND CHANGE MANAGEMENT POLICY

**Requirements Management Process**

**1. Repository Tool and Setup**

* **Platform:** Confluence (Cloud-based, secure environment aligned with SDLC standards).
* **Environment structure:** Distinct space separation between development workflows and production baselines.
* **Governance and naming:** Mandated file and page taxonomy following the [Department\_Type\_Detail\_Version] format, fully compliant with the Documentation Policy.

**2. Requirement Attributes Schema**

Each requirement documented in Confluence must include the following metadata fields:

* **Identification:** Unique ID, Requirement Name, Detailed Description.
* **Prioritisation:** MoSCoW tier classification (*Must, Should, Could, Won't*).
* **Ownership and lifecycle:** Originating Stakeholder, Status (*Proposed, In-Design, Ready for UAT, Implemented*).
* **Validation:** Acceptance Criteria.

**3. Traceability Framework and Rationale**

* **Business rationale:** Ensures all technical features strictly align with the $2M investment boundary for Initiative 1 and external vendor SLAs for Initiative 2, mitigating scope creep and enforcing financial limits.
* **Traceability mechanism:** Establishes bidirectional traceability matrix linking:
  + Initial Business Objectives
  + Business Requirements Specification (BRD)
  + Technical Agile Sprints
  + UAT Test Cases

**4. Change Control Process**

* **Submission:** Stakeholders must submit a formal Change Request form for any proposed modification.
* **Impact assessment:** Mandatory for any change impacting the $2M budget or the 30-day supplier payment terms.
* **Review and approval gates:**
  + Technical validation: Divya Sapra.
  + Financial authorisation: Anna Armstrong (formal signature required prior to updating the Confluence baseline).
